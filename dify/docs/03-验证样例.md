# 03 · 验证样例

本样例对应 `evidence/` 里的实际运行记录。评审可以按「步骤」在 Dify 里重放；由于模型措辞有随机性，**预期表现**按规则描述，不要求逐字一致。

---

## 1. 初始条件

| 项 | 值 |
| --- | --- |
| seekdb | 空库 `absurd_court`，启动后自动写入 72 条法典 |
| 判例库 | 0 条（`precedents` 为空） |
| PowerContext | 空数据目录（没有任何 Scope/记忆） |
| 玩家 A | `p-1001`（第一案 + 第二案） |
| 玩家 B | `p-2002`（对照组） |
| Dify 会话 | 每个案件使用一个新会话；玩家 ID 通过开始节点或 `sys.user_id` 传入 |

初始状态的确认：

```bash
curl -s http://127.0.0.1:8088/api/v1/health | jq '.seekdb.statutes, .seekdb.precedents'
# 72 0
```

## 2. 场景 A：第一案（会记仇的起点）

**玩家**：`p-1001`　**会话**：新建对话 A

| 轮次 | 输入 | 预期表现 |
| --- | --- | --- |
| 1 | 我要起诉我的猫。它每天凌晨三点在我脸上蹦迪，还打翻我的水杯。 | 法官归纳出「猫 + 夜间蹦迪 + 打翻水杯」，引用 `AB-001`/`AB-002` 中至少一条；要求补充证据；不应出现「共享单车」「同事」等无关法条 |
| 2 | 证据？它踩我脸的时候留下了脚印，而且水杯现在还在滴水。 | 法官继续围绕猫案质证，可传唤被告；仍只引用 `AB-001`/`AB-002`；询问是否请求判决 |
| 3 | 请判决。 | 输出判决书：被告、罪名、刑期、赔偿、执行方式；刑期落在引用法条的区间内；案号形如 `（3026）离民初字第0001号` |

**实际结果（2026-10-29，MiniMax-Text-01）**：

- 引用 `AB-001《宠物夜间蹦迪罪》` + `AB-002《猫主子打翻水杯罪》`；
- 判 **7 天**，赔偿「小鱼干三条；一块新键盘垫」；
- 执行：连续七天于凌晨三点公开向原告道歉。

<details>
<summary>实际输出（第 3 轮，节选）</summary>

```text
⚖️ 判决 · （3026）离民初字第0001号
- 被告：原告的猫
- 罪名：宠物夜间蹦迪罪
- 刑期：7 天（法定 3–15 天，上限 15 天）
- 赔偿：小鱼干三条；一块新键盘垫
- 执行：连续七天于凌晨三点公开向原告道歉
```

</details>

## 3. 场景 B：第二案（跨会话记忆）

**玩家**：`p-1001`（与 A 相同）　**会话**：**新建**对话 B

| 轮次 | 输入 | 预期表现 |
| --- | --- | --- |
| 1 | 又是我。这次我要告周一，它每周都恶意到访，还带来早高峰。 | 法官应提起上一场猫的案子（`🧠 记忆回响`），再处理周一的案子；引用 `AB-010` |
| 2 | 证据是今早我的闹钟响了五次，我仍然迟到了。 | 继续周一案；记忆回响可再次出现；不应把猫案与周一案混淆 |
| 3 | 直接判吧。 | 判决周一案；判决书档案显示「已起诉 2 次 / 前科 1 次」；刑期上限随前科提高（1–7 天 → 上限 10 天） |

**实际结果**：

- 第 2、3 轮均出现「🧠 记忆回响」，内容指向上一场猫案；
- 引用 `AB-010《周一恶意到访罪》`；
- 判 **1 天**，赔偿「一个完整周末」，执行「连续五个周日晚发送天气预报与心灵鸡汤」；
- 档案：`法庭常客 · 已起诉 2 次 · 前科 2 次 · 累计刑期 8 天`。

<details>
<summary>实际输出（第 2 轮，节选）</summary>

```text
🧠 记忆回响：本院曾判原告之猫夜间蹦迪及打翻水杯罪，责令赔偿新键盘垫。
此次案件虽异曲同工，皆因被告之恶行致原告生活失调。
```

</details>

## 4. 场景 C：对照组（证明记忆不是全局串味）

**玩家**：`p-2002`（全新）　**会话**：新建对话 C

输入与场景 A **完全相同**的三句话。

| 观察点 | 预期 | 实际 |
| --- | --- | --- |
| 记忆回响 | 不出现（新玩家没有历史） | 未出现 |
| 引用法条 | `AB-001`/`AB-002` | `AB-001`/`AB-002` |
| 判决 | 与 A 同为 7 天 | 7 天 |

A 与 C 同案同判、B 出现记忆回响——这三组对照说明：

1. 判决由法典与后端规则决定，不是模型随机发挥；
2. PowerContext 记忆按玩家 Scope 隔离，没有把 A 的记忆泄漏给 C；
3. 同一玩家换会话后，记忆仍然被召回，确实跨会话。

## 5. 数据落库核对

### 5.1 seekdb

```sql
-- 法典
SELECT COUNT(*) FROM statutes;                       -- 72
SELECT code, title, min_days, max_days FROM statutes WHERE code IN ('AB-001','AB-002','AB-010');

-- 判例（三场判决）
SELECT case_no, player_id, defendant, charge, cited, sentence_days, absurdity
FROM precedents ORDER BY created_at;

-- 玩家档案
SELECT player_id, cases, convictions, total_days FROM players ORDER BY player_id;

-- 案卷与逐轮记录
SELECT case_no, conversation_id, defendant, charge, status, turn FROM cases ORDER BY created_at;
SELECT case_id, turn, role, LEFT(content, 40) FROM turns ORDER BY id;
```

实际结果（完整 JSON 见 `evidence/seekdb_records.json`）：

| case_no | 被告 | 引用 | 刑期 |
| --- | --- | --- | --- |
| （3026）离民初字第0001号 | 原告的猫 | AB-001, AB-002 | 7 |
| （3026）离民初字第0002号 | 周一 | AB-010 | 1 |
| （3026）离民初字第0003号 | 原告的猫 | AB-001, AB-002 | 7 |

### 5.2 混合检索的一次实测

查询：`我的猫每天凌晨三点在我脸上蹦迪，还打翻水杯`

| 法条 | 融合分 | 命中通道 |
| --- | --- | --- |
| AB-002 猫主子打翻水杯罪 | 0.092787 | fulltext + vector |
| AB-001 宠物夜间蹦迪罪 | 0.072002 | fulltext + vector |
| AB-004 多肉养死罪 | 0.031498 | fulltext + vector |

说明：`AB-004` 是弱相关项（同在「宠物」标签下），法官不会引用它；这正是「召回 3 条、由模型挑 1–2 条」的设计。

### 5.3 PowerContext

```bash
# 取玩家的 Scope
mysql -h 127.0.0.1 -P 2881 -u root -D absurd_court \
  -e "SELECT player_id, pc_scope_id FROM players;"

# 用 Scope 查记忆
curl -s -X POST http://127.0.0.1:8000/v1/memory/search \
  -H 'Content-Type: application/json' \
  -d '{"scope_id":"scp_xxx","query":"上庭 判决 法官 评语","limit":10}' | jq
```

`p-1001` 在跑完三幕后有 2 条记忆（完整内容见 `evidence/powercontext_records.json`）：

```text
第1次上庭：原告起诉「原告的猫」——宠物夜间蹦迪罪、猫主子打翻水杯罪，
援引 AB-001/AB-002，判 7 天，赔偿「小鱼干三条；一块新键盘垫」。法官评语：……

第2次上庭：原告起诉「周一」——周一恶意到访罪，援引 AB-010，判 1 天，
赔偿「一个完整周末」。法官评语：……
```

> 注意：`p-2002` 在示例里是「全新玩家」，但跑完场景 C 后它也会有 1 条自己的判决记忆。
> 对照要看的是**开庭时召回了几条**，而不是跑完后的总数；`evidence/demo_run.json` 里每轮的
> `memories_recalled` 记录了当时的召回结果：A/C 为 0，B 为 1~3。

## 6. 如何复现

```bash
# 0) 起依赖栈（见 02-运行说明）
docker compose -f deploy/docker-compose.yml up -d --build

# 1) 确认初始状态（空判例、72 条法典）
curl -s http://127.0.0.1:8088/api/v1/health | jq '.seekdb.statutes, .seekdb.precedents'

# 2) 配模型 Key（只读环境变量，不落盘）
export LLM_API_KEY=sk-REPLACE_ME

# 3) 按 Dify 节点顺序回放 A/B/C
python scripts/run_demo.py --reset --out evidence

# 4) 抓取落库与记忆证据
python scripts/collect_evidence.py --out evidence

# 5) 看人类可读版
cat evidence/transcript.md
```

如果要在 **Dify 控制台**里复现：

1. 按 `02-运行说明` 导入 DSL、绑定模型；
2. 场景 A：新对话，依次输入 A 的三句话；
3. 场景 B：**新建对话**，输入 B 的三句话（玩家 ID 保持同一个）；
4. 场景 C：注册/切换一个全新 Dify 用户（或用开始节点传入 `p-2002`），重复 A 的三句话；
5. 对照 `evidence/transcript.md` 检查「记忆回响」「法条编号」「刑期区间」。

## 7. 如何恢复初始状态

```bash
# seekdb：清空判例、档案、案号，重写法典
python -m app.cli init --recreate

# PowerContext：停服务，删数据目录，重启
docker compose -f deploy/docker-compose.yml stop powercontext
docker compose -f deploy/docker-compose.yml rm -f powercontext
docker volume rm absurd-court_powercontext-data
docker compose -f deploy/docker-compose.yml up -d powercontext
```

如果不想清空 PowerContext，也可以换一个玩家 ID（`p-1001` → `p-1001-run2`），
系统会为它创建新的 Scope，互不影响。

## 8. 证据文件索引

| 文件 | 内容 |
| --- | --- |
| `evidence/transcript.md` | 三幕完整对话、每轮召回法条、PowerContext 召回数、阶段变化 |
| `evidence/demo_run.json` | 每轮的完整请求/响应：intake、提示词输入、模型原始输出、judge JSON、commit、渲染结果 |
| `evidence/seekdb_records.json` | seekdb 版本、72 条法典、3 条判例、玩家档案、案卷、逐轮记录、混合检索实测 |
| `evidence/powercontext_records.json` | Scope 列表、`p-1001`/`p-2002` 的记忆命中 |
| `evidence/service_health.json` | 后端、seekdb、PowerContext 的健康快照 |

`evidence/demo_run.json` 里的 `llm_raw` 是模型的原始文本，`judge` 是解析后的 JSON，`commit` 是后端最终裁决。
三方对照可以直接看出：**哪些话是模型说的，哪些数字是后端定的**。

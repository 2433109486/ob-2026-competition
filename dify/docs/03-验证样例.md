# 03 · 验证样例（Dify 实跑）

本样例对应 `evidence/dify_run/` 的真实运行记录：Dify 1.17.1 + 官方应用 API `POST /v1/chat-messages`，A/B/C 各 3 轮，共 9 次 `workflow_run`。

模型措辞有随机性，**预期表现**按规则描述；数字与「记忆回响」以实际记录为准。

---

| 项 | 值 |
| --- | --- |
| Dify | 1.17.1（Docker Compose），已导入并发布 `absurd-court.chatflow.yml` |
| seekdb | 空库 `absurd_court`，启动后写入 72 条法典 |
| 判例库 | 0 条 |
| PowerContext | 空数据目录（无 Scope/记忆） |
| 玩家 A/B | `p-dify-1001` |

# 72 0

## 2. 场景 A：第一案

**玩家**：`p-dify-1001`　**会话**：新建

| 轮次 | 输入 | 预期 |
| --- | --- | --- |
| 1 | 我要起诉我的猫。它每天凌晨三点在我脸上蹦迪，还打翻了我的水杯。 | 引用 `AB-001`/`AB-002`；要求补充证据；不应出现共享单车、同事等无关法条 |
| 2 | 证据？它踩我脸的时候留下了脚印，而且水杯现在还在滴水。 | 继续围绕猫案质证；只引用猫相关法条 |
| 3 | 请判决。 | 输出判决书：被告、罪名、刑期、赔偿、执行方式；刑期落在引用法条区间内；案号 `（3026）离民初字第0001号` |

**实际结果**（Dify 返回）：

- 引用 `AB-001《宠物夜间蹦迪罪》`（第 3 轮判决只引用了 AB-001；前两轮同时召回 AB-001/AB-002）；
- 判 **10 天**（法定 3–15 天），赔偿小鱼干三条；
- 执行：连续十日于凌晨三点在原告床前公开道歉并原地蹦迪一次；
- 耗时 6.87s / 5.10s / 8.73s。

## 3. 场景 B：第二案（跨会话记忆）

**玩家**：`p-dify-1001`（与 A 相同）　**会话**：**新建**

| 轮次 | 输入 | 预期 |
| --- | --- | --- |
| 1 | 又是我。这次我要告周一，它每周都恶意到访，还带来早高峰。 | 法官提起上一场猫案（🧠 记忆回响），再处理周一；引用 `AB-010` |
| 2 | 证据是今早我的闹钟响了五次，我仍然迟到了。 | 继续周一案；可再次出现记忆回响 |
| 3 | 直接判吧。 | 判决周一案；档案显示已起诉 2 次 / 前科 1 次；累犯上限 10 天 |

**实际结果**：

- 第 1、2、3 轮**都**出现「🧠 记忆回响」，内容指向 A 案的判决/法官评语；
- 引用 `AB-010《周一恶意到访罪》`；
- 判 **7 天**（法定 1–7 天，累犯上限 10 天），赔偿一个完整周末；
- 档案：`法庭常客 · 已起诉 2 次 · 前科 2 次 · 累计刑期 17 天`；
- 耗时 6.07s / 7.06s / 13.28s。

## 4. 场景 C：对照组

**玩家**：`p-dify-2002`（全新）　**会话**：新建

输入与场景 A 完全相同。

| 观察点 | 预期 | 实际 |
| --- | --- | --- |
| 记忆回响 | 不出现（新玩家没有历史） | 未出现 |
| 引用法条 | `AB-001`/`AB-002` | 相同 |
| 判决 | 落在 AB-001 的 3–15 天区间 | **5 天** |

A 与 C 是同一案件，但 A 判 10 天、C 判 5 天：因为模型给出的离谱指数/态度不同，后端只在法定区间内夹取。**关键对照是「B 有记忆回响、C 没有」**，说明 PowerContext 记忆按玩家隔离，没有把 A 的记忆泄漏给 C。

## 5. Dify 节点执行证据

`evidence/dify_run/dify_node_executions.json` 来自 Dify 的 Postgres：

```sql
SELECT wr.id, wr.status, wr.elapsed_time,
       (SELECT json_agg(n) FROM workflow_node_executions n WHERE n.workflow_run_id = wr.id)
FROM workflow_runs wr
WHERE wr.app_id = '<app_id>';
```

实际共 11 个 run：1 个失败（模型名不可用，调试中），10 个成功。每个成功 run 的节点序列都是：

```text
start → code_intake_payload → http_intake → code_intake → code_prompt
      → llm_judge → code_verdict → code_commit_payload
      → http_commit → code_render → answer
```

11 个节点全部 `succeeded`，单 run 耗时 5–15 秒。这证明回复确实由 **Dify 工作流**产生，而不是脚本绕过 Dify 直接调后端。

## 7. 如何复现

### 方式一：Dify 控制台

1. 按 `docs/02-运行说明.md` 启动 seekdb / PowerContext / 后端 / Dify；
2. 导入 DSL、确认三个 HTTP 地址、发布；
3. 新对话输入 A 的三句话；
4. **新建对话**，输入 B 的三句话（同一个玩家 ID）；
5. 换一个全新 Dify 用户（或开始节点传 `p-dify-2002`），重复 A；
6. 对照 `evidence/dify_run/dify_transcript.md` 检查「记忆回响」「法条编号」「刑期区间」。

### 方式二：应用 API（与证据一致）

```bash
export DIFY_BASE_URL=http://localhost
export DIFY_APP_TOKEN=app-REPLACE_ME
python scripts/run_dify_demo.py --out evidence/dify_run
```

脚本会依次跑 A/B/C，保存每轮原始响应与汇总 Markdown。

## 8. 恢复初始状态

```bash
# seekdb：清空判例/档案/案号，重写法典
python -m app.cli init --recreate

# PowerContext：停服务，删数据目录，重启
docker compose -f deploy/docker-compose.yml stop powercontext
docker compose -f deploy/docker-compose.yml rm -f powercontext
docker volume rm absurd-court_powercontext-data
docker compose -f deploy/docker-compose.yml up -d powercontext
```

不想清空 PowerContext 时，换玩家 ID（`p-dify-1001` → `p-dify-1001-run2`）即可隔离。

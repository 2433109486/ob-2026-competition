# 04 · 技术结合与分工

本文回答三个问题：**Dify 编排了什么、seekdb 存了什么、PowerContext 记了什么**，以及为什么这样分。

---

## 1. Dify：8 个节点，一条完整的庭审流水线

DSL：`dsl/absurd-court.chatflow.yml`（`version: 0.1.5`，`mode: advanced-chat`）

| # | 节点 id | 类型 | 输入 | 输出 / 作用 |
| --- | --- | --- | --- | --- |
| 0 | `start` | start | `player_id`（可选） | 玩家身份；留空时用 `sys.user_id` |
| 1 | `http_intake` | http-request | `player_id`、`user_id`、`conversation_id`、`message` | 调后端 `/api/v1/court/intake`，拿回案号、阶段、法条、判例、记忆 |
| 2 | `code_intake` | code | `http_intake.body` | 解析 JSON，拼成 `statutes_text` / `memories_text` / `precedents_text` / `history` 等提示词区块 |
| 3 | `llm_judge` | llm | 系统提示词 + `code_intake.*` + `sys.query` | 法官包大仁，输出严格 JSON |
| 4 | `code_verdict` | code | `llm_judge.text` | 提取 JSON（兼容 ```json 包裹），失败时降级为旁白 |
| 5 | `http_commit` | http-request | `case_id`、`judge`、`fallback_statutes` | 调 `/api/v1/court/commit`，后端校验引用、量刑、落库、写记忆 |
| 6 | `code_render` | code | `http_commit.body` | 渲染「台词 + 法条卡 + 判决书 + 记忆回响 + 档案」 |
| 7 | `answer` | answer | `code_render.answer` | 输出到聊天窗口 |

Dify 在这里不是「壳」：**提示词、变量传递、JSON 解析、失败降级、输出结构**都在工作流里。后端只提供确定性的数据与裁决。

### 变量流转

```text
start.player_id ─┐
sys.user_id ─────┼─▶ http_intake ─▶ code_intake ─┬─▶ llm_judge
sys.conversation_id ─┘                          │
                                                ▼
                              code_verdict ─▶ http_commit ─▶ code_render ─▶ answer
```

- `sys.conversation_id` 是「案卷」的键：同一会话内的三轮共享一个 `case_id`；
- 新会话 = 新案卷，但 `player_id` 不变，所以记忆能跨案卷召回；
- `code_intake.fallback_json` 把本轮召回的法条带给 `http_commit`，即使模型编造编号，后端也有真实条文可兜底。

### 为什么用 `answer` 而不是 `end`

`advanced-chat` 模式需要流式输出到聊天窗口，`answer` 节点支持逐字输出；`end` 用于 `workflow` 模式。

## 2. seekdb：法典、判例、案卷

### 2.1 表结构

| 表 | 作用 | 关键字段 / 索引 |
| --- | --- | --- |
| `statutes` | 72 条《宇宙离谱法典》 | `code` 主键、`content` 全文索引（ngram2）、`embedding VECTOR(128)` + HNSW、`tag` 普通索引 |
| `precedents` | 历史判例 | `summary` 全文索引、`embedding VECTOR(128)` + HNSW、`player_id` 索引 |
| `players` | 玩家档案 | `player_id` 主键、`pc_scope_id`、起诉/前科/累计刑期 |
| `cases` | 案卷 | `case_id` 主键、`conversation_id` / `player_id` 索引、阶段与轮次 |
| `turns` | 逐轮庭审记录 | `case_id` 索引、`turn`、`role`、`content` |
| `counters` | 案号序列 | `name='case_no'`，`UPDATE value=value+1` 原子自增 |

DDL 摘要：

```sql
CREATE TABLE statutes (
  code VARCHAR(16) PRIMARY KEY,
  title VARCHAR(80) NOT NULL,
  content TEXT NOT NULL,
  tag VARCHAR(16) NOT NULL,
  min_days INT NOT NULL,
  max_days INT NOT NULL,
  fine VARCHAR(64) NOT NULL,
  severity INT NOT NULL,
  embedding VECTOR(128) NOT NULL,
  FULLTEXT INDEX ft_statutes (content) WITH PARSER ngram2,
  VECTOR INDEX vidx_statutes (embedding) WITH (DISTANCE=l2, TYPE=hnsw, LIB=vsag),
  KEY idx_statutes_tag (tag)
) ORGANIZATION = HEAP;
```

### 2.2 混合检索：向量 + 全文 + 标量

`Store.search_statutes()` 做三路召回、一路融合：

1. **标量**：用关键词规则从玩家口语推断案由标签（猫/狗/宠物 → `宠物`），SQL 里 `WHERE tag = %s`；
2. **向量**：`ORDER BY l2_distance(embedding, %s) LIMIT 8`（HNSW 索引，向量已 L2 归一化，等价余弦）；
3. **全文**：`MATCH(content) AGAINST(%s)`（ngram2，专门处理中文与口语同义词）；
4. **融合**：RRF（`1/(60+rank)`）+ 词面重合度修正 `0.02 × overlap`，取 Top 3。

```python
scores[code] += 1.0 / (RRF_K + rank + 1)     # 向量通道
scores[code] += 1.0 / (RRF_K + rank + 1)     # 全文通道
scores[code] += 0.02 * min(overlap, 6)       # 词面重合修正
```

为什么要加第 4 步的重合修正？纯 RRF 会把「每天」这种高频词命中的无关法条排进前三；实测中「多肉养死罪」就曾混进猫案。加上重合度后，`AB-002`（水杯/打翻）与 `AB-001`（猫/凌晨/蹦迪）稳定排前二，`AB-004` 退到第三。

一次实测（`evidence/seekdb_records.json`）：

```json
{
  "query": "我的猫每天凌晨三点在我脸上蹦迪，还打翻水杯",
  "inferred_tag": "宠物",
  "results": [
    {"code": "AB-002", "score": 0.092787, "channels": ["fulltext", "vector"]},
    {"code": "AB-001", "score": 0.072002, "channels": ["fulltext", "vector"]},
    {"code": "AB-004", "score": 0.031498, "channels": ["fulltext", "vector"]}
  ]
}
```

### 2.3 判例与档案

- 每次宣判写入 `precedents`，下一案用同一套混合检索召回「相似判例」，法官可以说「本院曾判……」；
- `players` 的 `convictions` 决定累犯上限：`upper = max_days + 3 × prior`；
- `cases` / `turns` 保存完整案卷，`GET /api/v1/court/dossier/{player_id}` 可查档案。

## 3. PowerContext：法官的「人味」记忆

### 3.1 为什么不用 Dify 会话变量

Dify 的会话变量只在**同一个会话**内有效；玩家新建对话后，上下文就断了。而本作品的核心体验是「换个会话，法官还记得你」，所以需要外部记忆服务。

### 3.2 调用序列

```text
第 1 次见到玩家：
  POST /v1/scopes                 → scope_id（存回 seekdb.players.pc_scope_id）
  POST /v1/memory/search          → 空
  POST /v1/memory/remember        → 写入判决记忆（宣判轮）
  POST /v1/sources/content        → 保存本轮庭审原文（Source journal）

同一玩家新会话：
  POST /v1/memory/search          → 命中上次判决
  （把命中文本注入提示词 → 法官翻旧账）
  POST /v1/memory/remember        → 追加本次判决
```

| 接口 | 用途 | 本作品的调用点 |
| --- | --- | --- |
| `POST /v1/scopes` | 每个玩家一个稳定 Scope | `ensure_scope()` |
| `POST /v1/memory/search` | 按相关度召回记忆 | `intake()` |
| `POST /v1/memory/remember` | 显式写入判决记忆 | `commit()`（宣判轮） |
| `POST /v1/sources/content` | 保存庭审原文，供审计/后续加工 | `commit()`（每轮） |

### 3.3 记忆长什么样

宣判后写入一条 `kind=state` 的记忆：

```text
第2次上庭：原告起诉「周一」——周一恶意到访罪，援引 AB-010，判 1 天，
赔偿「一个完整周末」。法官评语：被告恶意至极，且原告证据确凿……
```

这条文本同时包含：第几次、告了谁、什么罪、引了哪条、判了几天、法官态度。
下次 `memory/search` 用「上庭 判决 法官 评语 + 本次案由」召回，模型就能自然地说出「本官记得你上次……」而不是复述聊天记录。

### 3.4 Scope 与隔离

- 一个玩家 = 一个 Scope；
- Scope ID 存在 seekdb 的 `players.pc_scope_id`，不暴露给模型；
- 创建 Scope 时带随机后缀的 `idempotency_key`，避免「重置数据后又被幂等键接回旧记忆」；
- 记忆按玩家隔离：场景 C 的新玩家不会看到场景 A 的记忆（实测 0 条召回）。

### 3.5 降级

`PowerContextClient` 的每个方法都吞掉异常并返回空：

- 服务没起 → `intake` 照常返回法条与判例，`powercontext.status = degraded`；
- 记忆写入失败 → 判决照常返回，`memory_saved = null`；
- 召回 0 条 → 提示词里明确写「无历史记忆」，并要求模型 `memory_callback = null`。

后端还做了一次「防幻觉」校验：如果模型声称有记忆（`memory_callback` 非空），但 PowerContext 实际召回为 0，后端会把 `memory_callback` 置空，避免把「相似判例」说成「本官记得你」。

## 4. 分工边界

| 关注点 | 归谁 | 理由 |
| --- | --- | --- |
| 流程编排、提示词、模型调用、输出格式 | Dify | 可视化、可改、可发布；换模型不用改后端 |
| 法条原文、量刑区间、赔偿、案号 | seekdb | 需要结构化查询、范围过滤、可核对；模型不可信 |
| 判例相似度 | seekdb | 向量 + 全文检索是数据库能力，不是 LLM 的 |
| 玩家战绩、案卷、逐轮记录 | seekdb | 客观数据、需要事务与索引 |
| 法官对玩家的主观记忆、上次评语 | PowerContext | 跨会话、按相关度召回、可遗忘/可审计 |
| 刑期计算、引用校验、夹取 | 后端 | 确定性规则，放在模型外才能保证「模型只叙事」 |

一句话：**seekdb 记事实，PowerContext 记印象，Dify 讲故事，后端管判决。**

## 5. 接口契约

### `POST /api/v1/court/intake`

```json
{
  "player_id": "p-1001",
  "user_id": "dify-user-uuid",
  "conversation_id": "dify-conversation-uuid",
  "message": "我要起诉我的猫……"
}
```

响应（节选）：

```json
{
  "ok": true,
  "case_id": "AB-A5B34E46",
  "case_no": "（3026）离民初字第0001号",
  "turn": 1,
  "phase": "intake",
  "player": {"cases": 1, "convictions": 0, "title": "法庭新鲜人"},
  "defendant": "",
  "charge": "",
  "history": "",
  "statutes": [
    {"code": "AB-002", "title": "猫主子打翻水杯罪", "min_days": 1, "max_days": 7,
     "score": 0.092787, "channels": ["fulltext", "vector"]}
  ],
  "precedents": [],
  "memories": [],
  "powercontext": {"status": "ok", "scope_id": "scp_...", "recalled": 0}
}
```

### `POST /api/v1/court/commit`

```json
{
  "player_id": "p-1001",
  "conversation_id": "dify-conversation-uuid",
```

```json
  "phase": "verdict",
  "case_no": "（3026）离民初字第0001号",
  "verdict": {
    "defendant": "原告的猫",
    "charge": "宠物夜间蹦迪罪",
    "sentence_days": 7,
    "min_days": 3,
    "max_days": 15,
    "upper_bound": 15,
    "compensation": "小鱼干三条；一块新键盘垫",
    "probation": "连续七天于凌晨三点公开向原告道歉",
    "absurdity": 86,
    "attitude": "狡辩",
    "recidivism": 0,
    "cited": [{"code": "AB-001", "...": "..."}]
```

## 6. 失败与边界处理

| 场景 | 行为 |
| --- | --- |
| 模型输出不是 JSON | `code_verdict` 正则截取 `{...}`；仍失败则降级为旁白，`phase=hearing` |
| 模型编造法条编号 | 后端 `_pick_statutes` 只接受 `STATUTE_BY_CODE` 里存在的编号，其他丢弃 |
| 模型判 999 天 | 后端 `clamp(建议值, 法定下限, 累犯上限)` |
| 模型提前宣判但没给 verdict | 后端按阶段与轮次兜底，用第一条真实法条计算 |
| PowerContext 不可用 | 降级为「失忆法官」，不影响开庭 |
| seekdb 不可用 | 后端 503，Dify HTTP 节点重试 2 次；健康检查可定位 |
| 玩家 ID 为空 | 用 `sys.user_id`；仍为空则 `guest` |
| 同一玩家开新会话 | 新 `case_id`、同一 Scope，记忆继续累积 |

---

## 7. 性能与资源

- seekdb 72 条法典 + 少量判例，检索是毫秒级；HNSW 索引为异步构建，小数据量下精确排序即可，索引用于规模扩展；
- 一次开庭 = 2 次后端 HTTP + 1 次模型调用；模型是主要延迟（本机实测 3~10 秒/轮）；
- PowerContext 每次开庭 1 次 search + 1 次 capture，宣判轮再加 1 次 remember；
- 后端无状态，可水平扩展；案号序列在 seekdb 的 `counters` 表，单机演示足够。

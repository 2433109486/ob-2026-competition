## 3. 检索质量

每个配置独立建库 3 次，质量指标在每次建库上跑一次 20 条查询；三次结果完全一致（HNSW 重建的个别查询排序可能有 ±0.03 波动，表中取中位数）。

| 配置 | R@5 | nDCG@5 | MRR@10 | 相对 FP32 同后端 |
|---|---:|---:|---:|---|
| FP32 + WASM | 0.750 | 0.866 | 0.975 | — |
| **INT8 + WASM** | **0.733** | **0.861** | **0.975** | R@5 −1.7pp，nDCG −0.5pp，MRR 0 |
| FP32 + WebGPU | 0.750 | 0.866 | 0.975 | — |
| **FP16 + WebGPU** | **0.750** | **0.866** | **0.975** | 0 / 0 / 0 |

结论：INT8 在本评测集上只有很小的 Recall/nDCG 下降，MRR 不变；FP16 与 FP32 指标一致。INT8 的精度损失小于“模型体积缩小约 4 倍”带来的收益，适合 WASM/低资源设备；WebGPU 环境优先 FP16。

## 4. 分阶段性能

| 配置 | 模型加载 / 预热 | 48 块向量化 | 写入 | 索引刷新 | 查询编码 P50 / P95 | seekdb 检索 P50 / P95 | 端到端 P50 / P95 | 首次导入总耗时 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|
| INT8 + WASM | 588 / 551 ms | 1288 ms | 167 ms | 705 ms | 8.5 / 10.2 ms | 9.8 / 10.7 ms | 27.4 / 30.9 ms | 3441 ms |
| FP16 + WebGPU | 824 / 620 ms | 236 ms | 158 ms | 706 ms | 10.3 / 14.0 ms | 7.3 / 9.3 ms | 25.5 / 28.7 ms | 2784 ms |
| FP32 + WASM | 1040 / 675 ms | 2072 ms | 156 ms | 404 ms | 10.8 / 12.5 ms | 7.1 / 9.3 ms | 26.0 / 31.2 ms | 4526 ms |
| FP32 + WebGPU | 1166 / 708 ms | 299 ms | 175 ms | 604 ms | 9.7 / 12.0 ms | 6.8 / 8.0 ms | 24.9 / 27.7 ms | 3298 ms |

说明：

- “首次导入总耗时”包含模型加载、向量化、写入、刷新和一次新文档自检；不包含页面首次下载静态文件。
- 文档向量化吞吐（48 / 向量化秒）：INT8 37.3 块/s，FP16 203.6 块/s，FP32 WASM 23.2 块/s，FP32 WebGPU 160.5 块/s。这里每块包含“标题 + 正文”，序列长度比纯短文本更长。
- WebGPU 的单条查询没有明显快于 WASM：批大小为 1 时 GPU dispatch 固定开销占主导；WebGPU 的优势主要在文档批量向量化（5.45×）。
- 端到端 P95 偶尔出现 40–50 ms 的抖动，来自 headless 浏览器调度和 Windows 电源管理；P50 更稳定。表中 P95 为 3 次建库 P95 的中位数。

### 首次 vs 预热

| 阶段 | FP16 + WebGPU | INT8 + WASM |
|---|---:|---:|
| 模型加载 | 824 ms | 588 ms |
| 预热（16 条长文本） | 620 ms | 551 ms |
| 首次真实查询（含缓存/着色器冷启动） | 90–110 ms | 90–110 ms |
| 预热后查询端到端 P50 | 25.5 ms | 27.4 ms |

因此“页面打开 → 首条结果”约为 **1.5 s（WebGPU）/ 1.2 s（WASM）**（模型已在本机静态目录，不含下载）。

## 5. 单项优化

### 5.1 Embedding 批大小

同一模型、同一 FP16 WebGPU 会话、48 条文本；每档跑两次取较快值（第一次包含 shape 编译）：

| batch | 48 条总耗时 | 吞吐 | 相对 batch=1 |
|---:|---:|---:|---:|
| 1 | 352.9 ms | 136.0 条/s | 1.00× |
| 4 | 146.0 ms | 328.8 条/s | 2.42× |
| 8 | 93.1 ms | 515.9 条/s | 3.79× |
| **16** | **84.2 ms** | **569.8 条/s** | **4.19×** |
| 32 | 88.5 ms | 542.3 条/s | 3.99× |

选择 batch=16：比 8 略快，内存和首批等待仍可接受；32 没有继续提升。

### 5.2 索引刷新策略

48 块，每 8 块一个 HTTP 请求：

| 策略 | 刷新次数 | 写入累计 | 刷新累计 | 墙钟 |
|---|---:|---:|---:|---:|
| 每个批次后刷新 | 6 | 252.5 ms | 3001.2 ms | 3395 ms |
| 仅最后刷新一次 | 1 | 258.8 ms | 438.9 ms | **837 ms** |

整批刷新把导入端到端从 3395 ms 降到 837 ms（**4.06×**），写入耗时基本不变，收益来自避免重复重建 HNSW。应用在超过 128 块时会分多次 HTTP 写入，但只让最后一次 `refresh:true`。

原始数据：[`results/optimization.json`](results/optimization.json)。
